## Do MArk or Spock route to serverless only the load above ready VM capacity, and do they feed a forecast into the routing decision?

**Overflow-only routing: yes for both.**
- **Spock.** The routing rule is a free-slot test: "When a request is submitted, the RM first tries to schedule it on any available VM which has free slots (we refer to free slots as free vCPUs). If a free VM is not available, it redirects the request to be run in a new lambda function." (§IV-B, p. 203). Results confirm the split: "VMs efficiently handle all requests in the average arrival rate, whereas request that arrive in sudden bursts are offloaded to lambda." (§V-B).
- **MArk.** The test is deadline-based, not a slot count: "On each running EC2 instance, there is a Bouncer monitoring serving metrics and performing request admission control. If an incoming request cannot be served within a specified time RTmax, it will be handled by Lambda instances immediately." (§4.1). The effect is the same: only what the running VMs cannot serve in time goes to Lambda.

**Forecast in the routing decision: no for both.** The forecast sizes the VM tier. The routing decision stays reactive.
- **MArk.** The predictor feeds provisioning: "MArk periodically measures the workload metrics, such as the request arrival rate, and sends them to a Proactive Controller which makes predictions and plans instances in advance" (§4.1). Algorithm 1 sets instance counts from F, "the predicted maximum request arrival rate for the next m steps" (§4.3). The Bouncer's Lambda decision uses no forecast.
- **Spock.** The forecast sizes the VM count. The predictor is a moving-window linear regression over t+t_startup (§IV-B.2). "Spock spawns additional VMs only based on the output from the predictor." (§IV-B.2).
- **Wording that could be misread.** In §IV-A.2 Spock's load balancer "uses the predicted load from the scaling policy to decide the resources required to be active over each monitoring period ... while balancing the load between VMs and lambdas". This is the forecast determining how many resources are active. The per-request VM-or-lambda choice is still the free-slot rule above.
- **Spock also has a reactive scale-out policy** (§IV-B.1) and evaluates reactive and predictive scale-out against each other (§V). The paper's claim that its design "lets us measure the effect of the forecast alone" is therefore not unique to the paper in spirit.

**What the paper can say it does differently.**
- It uses Kubernetes pods as the base tier, not VMs.
- It runs a paired reactive/predictive comparison (S3 vs S4) with the same router.
- It reports validity gates on every run.

**The other two hybrids in the paragraph.**
- **PulseNet** also routes only overflow. Its Load Balancer uses a regular instance if one is available and otherwise sends the request to the expedited track. Its standard track scales from windowed metrics (no forecaster) with IAT-based filtering of burst metrics (§4.3).
- **LA-IMR** routing does use a model-predicted latency from a smoothed arrival rate. Algorithm 1 scales out while replicas are below the cap and otherwise offloads a fraction, "if g_hat > tau_m (predicted SLO breach) then if N < N_max then scale out one replica else offload fraction phi upstream". Point 1 of the paper's claim holds there only loosely, and point 2 differs (the predicted latency enters both the replica decision and the offload decision).

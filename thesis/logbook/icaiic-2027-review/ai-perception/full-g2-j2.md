Accuracy. Table II reports the error on the test portion at the 9-step horizon, in RPS of the replayed series, with the standard deviation over three seeds. Skill is the share of the error of a persistence forecast, which repeats the last observed value, that a model removes. The GRU has a skill of 0.216. Its error is slightly lower than that of an LSTM, the predictor family of ElaX, selected in the same way. The final LSTM was trained on the training plus validation portions and the final GRU on the training portion, which favours the LSTM. The GRU does not beat a linear autoregression on the same inputs. We also screened 12 variants: input transforms, a target transform, coarser sampling intervals, a decomposed input and two other architectures. None of them beat the linear model on the folds that we used for selection.

Sample 5:
Leak-free protocol. The ClarkNet HTTP trace [26] is aggregated into 15 s buckets and multiplied by 33, the factor that the replay uses. We split the series in time order into training, validation and test portions. A gap of 38 samples (input length plus horizon minus one) at each boundary, the embargo, ensures that no input window or target spans two portions. The input normalization is fitted on the training portion. We select the hyperparameters and the epoch budget on the validation portion with the Tree-structured Parzen Estimator [27] of Optuna [28]. The test portion stays out of the selection, because a score from data that also guided the selection is biased [29]. We then train the selected configuration with three seeds and evaluate each model once on the test portion. The 20-minute window that the experiments replay lies inside the test portion, so the deployed model never saw it.

Sample 6:
Scenarios and batches. Table II lists the four scenarios. In the scenario batch, S1, S2, S3 and S4 ran five × each. The comparison of S4 with S3 then ran in pairs. The two runs of a pair start from one static worker and use the same provisioning delay, which cycles through 60, 90, 120, 75 and 45 s from pair to pair. The order of S3 and S4 alternates between pairs (counterbalancing), so drift of the host does not favour one arm. Three paired batches used the leak-free GRU of Section IV A (5 pairs), B (10 pairs) and C (10 pairs). Each batch recorded its primary endpoint and its test level in the run profile before the first run. B and C ran the same ten-pair profile. B ran while other processes loaded the host, so C repeated it on a quieter host, and we treat C as the confirmatory batch. An earlier batch of five pairs showed a significant advantage for S4. Its run manifests do not identify the predictor, and the predictor of that period was trained on a synthetic trace, so we do not count it as evidence for the leak-free GRU.

Sample 10:
Tests and validity. The primary endpoint is the per-run p99, the 99th percentile of all request latencies in one run. For the paired batches we use a one-sided exact paired permutation test (alternative: S4 is faster) at a level of 0.05, a bootstrap 95% interval and the paired Cohen's d. A run counts when it passes validity checks. A hybrid run must engage the node tier: a pod must become unschedulable or a dynamic node must be provisioned. An S4 run must also receive every eligible forecast, have a horizon that covers the provisioning delay, and change the replica target through a forecast at least once. Every run of the three paired batches passed (10 of 10, 20 of 20 and 20 of 20), and batch C received 570 of 570 forecasts. Batches B and C also record the CPU-busy fraction of the host, the share of non-idle CPU time sampled from `/proc/stat` during a run.

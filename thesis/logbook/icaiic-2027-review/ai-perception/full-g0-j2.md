Sample 1:
ElaX [6] makes the first decision, the pod count, from a forecast for one container cluster. Once an hour an LSTM predicts the load of the next 60 minutes. ElaX reserves resources for the largest predicted value through a linear resource model, and a slack-based controller corrects the reservation online. ElaX does not split traffic between backends, and its hourly horizon is long next to the minute-scale surges of web traffic.

Sample 2:
This paper asks whether ElaX's forecast-driven scaling decision still helps inside a hybrid, where the serverless backend already takes load during the provisioning delay. MArk [7] and Spock [8] have this structure on virtual machines: a forecast sizes the machines, and requests that the machines cannot serve go to serverless functions. We build it on Kubernetes pods and Knative, a serverless platform that runs on Kubernetes, and we run the same router with and without the forecast. The contributions are the following. + A control architecture in which one 15 s loop runs a capacity-aware router (Algorithm 1) and a replica scaler (Algorithm 2) for Kubernetes and Knative, under a service-level objective (SLO) of 200 ms for p99. + An extension of ElaX's scaling decision with multi-step GRU forecasts. A GRU replaces the LSTM, forecasts nine 15 s steps and refreshes in every cycle. The scaler sizes for the largest value of the forecast plus a margin (the upper envelope) over 135 s. The router does not read the forecast. We train and test the GRU under a leak-free protocol: no test data, and no data that overlaps a split boundary, enters training or tuning. + An evaluation in two parts. A scenario batch compares the reactive hybrid (S3) and the predictive hybrid (S4) with Kubernetes under the HPA (S1) and with Knative alone (S2). Paired batches then compare S4 with S3, with validity checks on every run.

Autoscaling with forecasts. HyPA combines reactive and model-based horizontal scaling and refits its model when the forecast error rises [11]. KAPETÁNIOS adapts HPA parameters through a digital twin of the cluster [12]. Forecast-based scalers for Kubernetes use time-series models of CPU use [13] or of the request rate [14]. AAPA adds archetype awareness and uncertainty estimates for serverless workloads [15], and ADAPT estimates the cold-start duration online and sets its planning horizon from it [16]. Each of these systems scales one platform. A recent benchmark finds that a calibrated rule-based autoscaler beats six deep reinforcement learning algorithms on cost [17].

Sample 5:
A Kubernetes deployment scales on load it has already seen. The Horizontal Pod Autoscaler (HPA) compares CPU use with a target and adds pods, the running copies of a service, only after the target is crossed [1]. If the cluster is also out of nodes, the wait is longer. A new virtual machine takes one to two minutes to boot [2], and on our testbed the first new node was ready 50 to 125 s after the request. Requests queue in that window, and the 99th-percentile latency (p99) climbs. Serverless platforms add instances within seconds [3]. Each new instance still pays a cold-start delay [4]. Public platforms also charge a higher unit price plus a fee per invocation [3], and steady load costs several × more there than on virtual machines [5].

Sample 7:
A hybrid deployment uses both. Reserved machines serve the stable base load, and serverless functions serve the excess [5]. A hybrid of Kubernetes and a serverless backend makes two decisions in every control cycle: how many Kubernetes pods to run, and what share of the traffic to send to the serverless backend. The two decisions interact. A pod that is added early lowers the serverless share. A serverless backend that absorbs a burst also masks the latency cost of a pod that is added late.

Sample 10:
Kubernetes adds pods only after the load has risen, so requests wait while new pods and nodes start. A serverless platform adds instances within seconds but costs more per request. A hybrid uses both. Kubernetes serves the base load, and the serverless platform takes the overflow. We ask whether a load forecast still helps in such a hybrid. Every 15 s, our control loop sends to Knative only the load that the ready Kubernetes pods cannot serve, and a scaler derived from ElaX sets the number of pods. In the predictive hybrid, the scaler also reads a 135 s forecast from a gated recurrent unit (GRU), plus a safety margin, and adds pods before the load arrives. The reactive hybrid has no forecast. We replayed the ClarkNet trace against both hybrids, Kubernetes with the Horizontal Pod Autoscaler (HPA), and Knative alone. Both hybrids matched the projected cost of Kubernetes with the HPA, but the reactive hybrid had a higher 99th-percentile latency (p99). Knative alone had the lowest p99 at more than twice the cost. In ten planned pairs of runs, the forecast changed p99 by -13.6 ms (95% CI [-63.5, +35.6], p = 0.307) and used 45% more pod-seconds. This design detects differences above about 72 ms, and the GRU forecast was no more accurate than a linear autoregression. These results suggest that in a hybrid, the serverless backend already serves the load while new pods start, so a forecast has little delay left to cover.

Sample 11:
Hybrid execution. The closest systems pair virtual machines with serverless functions. MArk provisions virtual machines from a load forecast and serves on AWS Lambda the requests that the machines cannot serve in time [7]. Spock sizes virtual machines from a forecast, uses serverless functions to cover their scale-out lag, and compares a reactive with a predictive scale-out policy [8]. In both systems the forecast sizes the base tier, and the overflow rule does not read it. Our design has the same split. It differs in the base tier, which is Kubernetes pods with a node tier under them, and in the evaluation, which keeps one router and pairs runs with and without the forecast. PulseNet sends a request to fast, disposable instances when no regular Knative instance is free [9], so both of its tracks are serverless. LA-IMR routes inference requests across edge and cloud tiers and scales Kubernetes replicas from a predicted latency in one controller [10].
